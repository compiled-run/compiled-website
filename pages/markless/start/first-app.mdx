The rest of this page gets a blank app of your own running. One command, four questions, and the
scripts you live in. There is no configuration step, and nothing to wire up afterwards.

**`npm create markless@latest` writes a working app.** After that, `dev`, `build` and `preview` are
the whole workflow.

```sh
npm create markless@latest
```

That is the whole command. It fetches whatever `create-markless@latest` resolves to on the day you
run it. This site was written against `0.3.2`. Then an interactive flow asks four things, before it
writes a single file.

## Four questions, then a summary you can cancel

**What are you building today?** Four starting points, each one a real project rather than an empty
folder:

*Learn Markless* is a small TSRX counter app. It is the best first project. *Build an app* is a
routed app with a `document.tsrx` shell plus 404 and 500 pages.

*Write docs* is an MDX docs site with a layout and sidebar components. *Full-stack app* is the
routed app plus `api/` and `middleware/` files.

**What should we call it?** The folder name. It is also the package name.

**Where should it run?** Node, Deno or Bun, in that order. Node is the one to take if you are not
sure.

**Should I install dependencies and initialize git?** Two yes or no questions.

Then it shows a `Ready to create?` summary and waits. Nothing has been written yet at that point.
Reading the summary and cancelling costs you nothing.

```json
{
	"overrides": {
		"@tsrx/core": "0.1.58"
	}
}
```

On Bun the same pin is written as `"resolutions"`. On pnpm it is `"pnpm": { "overrides": { ... } }`.
The version to pin is `0.1.58`. It is the last release before the dependency on the missing package
was added.

## What you get, file by file

```txt
my-app/
  document.tsrx           the HTML shell every page is rendered into
  pages/                  one file per route
  api/                    server handlers, full-stack starter only
  middleware/             request middleware, full-stack starter only
  public/                 files served as they are
  components/             shared components, docs starter
  scripts/markless-doctor.mjs
  markless-router-env.d.ts
  tsconfig.json
  vite.config.ts
  package.json
```

Two of those are worth opening straight away.

**`pages/` is the router.** A file at `pages/index.tsrx` is the page at `/`, and a file at
`pages/about.tsrx` is the page at `/about`. There is no route table to keep in step with the folder.
The folder is the route table.

`vite.config.ts` is the entire build configuration. It is two plugins long:

```ts
import { markless } from '@markless/core/vite';
import { router } from '@markless/router/vite';
import { defineConfig } from 'vite-plus';

export default defineConfig({
	plugins: [markless(), router()],
});
```

The first plugin compiles `.tsrx` files. The second one turns `pages/` into routes and owns the
server. Nothing in that file mentions your components. Adding a page never means editing it.

## The scripts are the workflow

`npm run dev` is the development server, with your changes appearing as you save.

`npm run build` makes the production build, into `.output/`.

`npm run preview` serves that production build, so you can see what a reader will actually get.

`npm run check` typechecks the project, including inside your `.tsrx` files.

`npm run doctor` checks the environment and the dependency versions, then runs a build.

`dev` is where you will live. `preview` is the one people forget. It serves the real output. That is
how you find anything that only shows up in a production build.

**`doctor` is for the setup, not the code.** It checks that the `@markless/*` packages are present.
It also checks that their versions match each other.

That match matters. Mismatched versions mean the compiler and the runtime disagree about the format
they pass between them. Run `doctor` first when an install or a production build misbehaves, before
you start reading your own code.

## When it is running

`npm run dev` prints a local URL. Open it and a counter is running on your machine, the same one
the front page of this site uses. Now you can break it: change the label, add a second button, save, and
watch the page keep up.

That is the whole setup. Everything after this point is about what goes inside `pages/`. When
the counter starts feeling small, the music player at the top of this page is the next target:
steal from its source freely.
