# A value you work out is never out of date

<PageMeta level="Start here" time="6 min" assumes="state" sprite="spiral" />

Everybody has shipped this bug. Two numbers on a screen disagree with each other, because one of
them was updated and the other one was supposed to be updated at the same time and was not. The
cart says three items and the total says the price of two. The code that was meant to keep them in
step is somewhere, and it is right nine times out of ten.

The reason that bug exists is that the total was stored. Storing it made it a second source of
truth that somebody has to maintain.

**If a value can be worked out from other values, do not store it. Work it out.** That is what
`computed()` is for.

```tsrx
const total = computed(() => shirts * 20 + mugs * 8);
```

You read `total` like any other variable. You never call it, you never pass it a list of the things
it depends on, and you never tell it that something changed. The compiler read the body, so it
already knows that this value is made out of `shirts` and `mugs`.

Here is that running. Add a shirt, wait a beat, then add a mug, and watch the total:

<CartTotalDemo />

Now read the file, and go looking for the line that updates the total:

```tsrx
import { computed, state } from '@markless/core';

export default function CartTotal() @{
	let shirts = state(1);
	let mugs = state(0);
	const total = computed(() => shirts * 20 + mugs * 8);

	<section>
		<p>Shirts at 20 each: {shirts}</p>
		<p>Mugs at 8 each: {mugs}</p>
		<p>Total: {total}</p>
		<button onClick={() => shirts++}>Add a shirt</button>
		<button onClick={() => mugs++}>Add a mug</button>
	</section>
}
```

There is not one. The two buttons change a quantity and stop there. The total is not a thing that
gets updated, it is a description of how to work the total out, and the only moment it is ever
worked out is a moment when something on screen actually needs it.

## Nothing runs until the screen asks for it

That last clause is not a detail, it is the design. The specification states the invariant:

> The entire graph is demand-driven from the DOM. State to computed to DOM updates, where
> compiler-generated DOM update symbols are the only effects in the system. Nothing computes unless
> the screen needs it.

That is from `specs/framework/03-state-graph.md`. Read practically, it means a `computed()` costs
you nothing while nothing is looking at it, and it means a value on screen cannot lag behind its
inputs, because being on screen is exactly what causes it to be worked out.

## Two rules, and then you know this

**Do not write to a computed.** It is derived, so assigning to it would be claiming two different
answers at once. Change the values it is made from instead.

**Do not declare something as state if you could derive it.** A good tell: if you find yourself
writing a line whose only job is keeping one variable agreeing with another, the second one wanted
to be a `computed()`.

## Where to go next

If you take one habit from this page, take the tell above: a line whose job is keeping two
variables in agreement is a `computed()` waiting to be written. You do not have to spot it in
advance. You will notice it the second time you write it.

If you have not read [State](/markless/concepts/state) yet, read that first, since everything here
sits on top of it. Otherwise the next unfamiliar thing on the list is
[Reading a .tsrx file](/markless/start/reading-tsrx), which is the short page on the three bits of
syntax these samples use.
