# A value you work out is never out of date

<PageMeta level="Start here" time="4 min" assumes="state" sprite="spiral" />

<ThemeToggle />

Everybody has shipped this bug. Two numbers on a screen disagree with each other. One of them was
updated, and the other was supposed to be updated at the same time and was not.

The cart says three items and the total says the price of two. The code that was meant to keep them
in step is somewhere, and it is right nine times out of ten.

That bug exists because the total was stored. Storing it made it a second source of truth, and
somebody has to maintain it.

**If a value can be worked out from other values, do not store it. Work it out.** `computed()` is
the word for that.

```tsrx
const total = computed(() => shirts * 20 + mugs * 8);
```

You read `total` like any other variable. You never call it. You never pass it a list of the things
it depends on, and you never tell it that something changed. The compiler read the body, so it
already knows this value is made out of `shirts` and `mugs`.

Here is that running. Add a shirt, wait a beat, then add a mug, and watch the total:

<CartTotalDemo />

Now read the file, and go looking for the line that updates the total:

```tsrx
import { computed, state } from '@markless/core';

export default function CartTotal() @{
	let shirts = state(1);
	let mugs = state(0);
	const total = computed(() => shirts * 20 + mugs * 8);

	<section>
		<p>Shirts at 20 each: {shirts}</p>
		<p>Mugs at 8 each: {mugs}</p>
		<p>Total: {total}</p>
		<button onClick={() => shirts++}>Add a shirt</button>
		<button onClick={() => mugs++}>Add a mug</button>
	</section>
}
```

There is not one. The two buttons change a quantity and stop there.

The total is not a thing that gets updated. It is a description of how to work the total out. It is
only ever worked out when something on screen actually needs it.

## Nothing runs until the screen asks for it

That last sentence is not a detail. It is the design. The whole graph is driven by demand from the
page: state feeds computed values, computed values feed the DOM, and updating the DOM is the only
effect in the system. Nothing computes unless the screen needs it.

Two things follow. A `computed()` costs you nothing while nothing is looking at it. And a value on
screen cannot lag behind its inputs, because being on screen is what causes it to be worked out.

## Two rules, and that is all of them

**Do not write to a computed.** It is derived, so assigning to it would be claiming two different
answers at once. Change the values it is made from instead.

**Do not declare something as state if you could derive it.** Here is the tell. You write a line
whose only job is keeping one variable in agreement with another. That second variable wanted to be
a `computed()`.

## Where to go next

If you take one habit from this page, take the tell above. A line whose job is keeping two variables
in agreement is a `computed()` waiting to be written. You do not have to spot it in advance. You
will notice it the second time you write it.
